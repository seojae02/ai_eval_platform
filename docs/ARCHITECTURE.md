# 구조 설명 (ARCHITECTURE)

이 문서는 플랫폼이 **어떤 부품으로 되어 있고, 제출 한 건이 어떻게 흘러가며, 왜 그렇게 만들었는지**를 처음부터 따라 읽을 수 있게 정리한 것입니다.
코드를 읽기 전에 이 문서를 먼저 보고, 각 절 끝의 "읽을 파일"로 넘어가면 됩니다.

- 기준: 2026-11-25, 테스트 699개(실제 샌드박스 1개 포함)
- 표기: **[RFP n쪽]** = 요구사항 문서 근거, **[가정]** = RFP에 없어 우리가 정한 것
- 예시 인물은 모두 가상입니다(가상학생01, 가상조교01, 가상교수01).
- 저장소의 예시 대회는 `demo/`의 손글씨 숫자 하나입니다(demo_stu01~11). 본문의 "와인·주택 가격·행위 인식·UCI Adult 데모 학생NN"은 개발 중 검사를 시험하려고 만들었던 과제의 사례이고, 제출용 저장소에서는 지웠습니다(결과는 근거로 남김).

## 1. 한 장 요약

```
                   브라우저 (참여자 · 관리자1 · 관리자2)
                         │  HTTP(S), CSRF, 세션 쿠키
                         ▼
 ┌───────────────────────────────────────────────┐
 │ web (Django)                                  │   화면·권한·규칙 검사. 채점·실행은 하지 않는다
 │  accounts · competitions · submissions · audit│
 └───────────────┬───────────────────────────────┘
                 │ 읽기/쓰기 (Job 줄 추가만)
                 ▼
 ┌──────────────────────┐      ┌──────────────────────────┐
 │ db (PostgreSQL 17)   │◀────▶│ worker (같은 Django 코드)  │  Job을 하나씩 가져가 처리
 │  모든 상태 + Job 큐   │      │  채점 → 검증(V1~V7) → 정리  │  외부 요청을 받지 않는다(포트 없음)
 └──────────────────────┘      └────────────┬─────────────┘
          ▲ 같은 storage 폴더                  │ tcp://docker-proxy:2375 (내부 전용 네트워크)
          │ (정답·제출 파일)                    ▼
                                 ┌──────────────────────────┐
                                 │ docker-proxy              │  /containers API만 허용
                                 └────────────┬─────────────┘  (이미지·볼륨·exec·빌드 차단)
                                              ▼
                                 ┌──────────────────────────┐
                                 │ sandbox 컨테이너 (제출마다) │  참여자 노트북·모델 실행
                                 │ 네트워크 없음 · 읽기 전용    │  끝나면 볼륨까지 삭제
                                 └──────────────────────────┘
```

**핵심 원칙 다섯 가지**

1. **web은 판단만, 무거운 일은 worker가.** 채점·노트북 실행은 웹 요청 안에서 하지 않는다. 그래서 채점이 느려도 화면이 멈추지 않고, 정답 파일을 읽는 코드가 worker 쪽에 모인다.
2. **상태는 DB 한 곳에.** 제출 횟수, 순위, 작업 큐를 따로 저장하지 않고 DB의 상태 칸으로 계산한다. 값이 실제와 어긋날 수 없다.
3. **참여자 코드는 믿지 않는다.** 노트북과 모델은 격리된 샌드박스에서만 실행한다. 그 결과도 형식 검사를 다시 거친다.
4. **시스템은 판정하지 않는다.** 검증은 근거(일치율, 의심 표시)만 만들고, 판정은 관리자1 제안 → 관리자2 결정이다.
5. **규칙은 services, 화면은 views.** 규칙(R1~R15)은 `services.py`류 파일에 있고, 뷰는 권한 확인과 화면만 맡는다. 서비스 함수는 `now`(현재 시각)를 인자로 받아서 테스트가 "16:59:59에 시작" 같은 상황을 그대로 만든다.

## 2. 컨테이너 5개 (docker-compose.yml)

| 서비스 | 하는 일 | 열린 길 | 왜 이렇게 |
|---|---|---|---|
| `db` | PostgreSQL 17. 모든 데이터와 작업 큐 | 내부망만(외부 포트 없음) | 큐까지 DB에 두면 구성 요소가 하나 줄고, worker가 죽어도 작업이 남는다(D2) |
| `web` | Django. 화면·권한·업로드·규칙 | `127.0.0.1:8000`만 | 외부에 열리는 유일한 서비스 |
| `worker` | `manage.py run_worker`. 채점·검증·정리 | 포트 없음. db, docker-proxy에만 | 외부 요청을 받지 않으므로 공격받을 입구가 없다 |
| `docker-proxy` | Docker 소켓 앞의 문지기 | `sandbox-control` 내부망. web은 이 망에 없다 | Docker 소켓 = 호스트 root 권한. worker도 소켓을 직접 갖지 않는다 |
| `sandbox-image` | 샌드박스 실행 이미지를 빌드만 함 | 네트워크 없음 | `docker compose build` 한 번으로 모든 이미지가 준비되게 |

운영 모드(`docker-compose.prod.yml`)는 web을 gunicorn으로 바꾸고, `DEBUG=False`로 하고, 코드 폴더를 연결하지 않으며, 업로드 파일을 이름 있는 볼륨에 둔다.

## 3. 제출 한 건의 여정 (가장 중요)

가상학생01이 유방암 과제(1차 마감 11/20 17:00, 3회)에 제출한다고 하자.

```
① 16:58:12 [제출 시작]                       web  submissions/services.py start_submission
   - 시작 시각을 서버가 기록 (R1: 마감 판정 기준)
   - 소속 줄(CompetitionMember)을 행 잠금 → 같은 사람의 동시 요청은 한 줄로 선다 (R6)
   - 이 구간 사용 횟수 = '업로드 중·채점 대기·채점됨'인 제출 수. 3 미만이면
   - Submission(상태: 업로드 중) 생성 → 1회를 '잡아 둔다'

② 16:58~17:01 파일 3개를 1MB 조각으로 전송      static/js/upload.js → services.receive_chunk
   - 조각마다 '마지막 수신 시각' 갱신 → 10분 동안 안 오면 만료 (D3)
   - 크기 상한 초과 → 형식 오류 → 잡아 둔 1회가 풀린다 (R3)

③ 17:01:40 [제출 완료]                       services.complete
   - 내용 검사: CSV(컬럼·행 수·id·허용 값, R15), 노트북(nbformat 스키마), 모델(앞 8바이트)
   - 통과 → 채점 대기 + 같은 트랜잭션에서 Job(채점) 등록
   - 시작이 16:58이라서, 수신이 마감 뒤(17:01)에 끝나도 1차 마감 구간으로 채점된다 (R1)

④ worker: 채점 Job                            jobs/queue.py → submissions/scoring.py
   - SELECT ... FOR UPDATE SKIP LOCKED 로 Job 하나 가져감
   - 정답과 id로 맞춰 지표 계산(Accuracy/Macro-F1/RMSE/MAE) → 채점됨, 점수 저장
   - 같은 트랜잭션에서 Job(검증) 등록
   - 실패하면 10초·20초 뒤 재시도, 3번째 실패 → 시스템 오류(횟수 미차감, R4)

⑤ worker: 검증 Job                            verification/services.py
   - V2·V3·V4: worker 안에서 파일 비교·정적 분석
   - V5: 샌드박스 컨테이너 ①에서 모델 로드 → test.csv 예측 → 제출 CSV와 비교
   - V1: 샌드박스 컨테이너 ②에서 노트북을 처음부터 실행 → 나온 CSV와 제출 CSV 비교
   - VerificationReport 저장 (전체 판정: 문제 없음/주의/의심/판정 불가)

⑥ 리더보드에 반영                              submissions/leaderboard.py
   - 참여자별 최고점 1개, 공동 순위(1·2·2·4), 참여자 화면은 '참여자 K7QM' 같은 별칭

⑦ 관리자1(가상조교01): 검토 목록 → 리포트·노트북 보기 → '부적합 제안' + 사유   submissions/review.py
   - 제안만으로는 순위가 그대로 (R11). 참여자 화면에는 '검토 중'

⑧ 관리자2(가상교수01): '부적합' 결정
   - 이 기록은 리더보드에서 빠지고, 가상학생01의 다음 기록이 대표가 되어 검토 목록에 오른다 (R12)
   - 제출 상태는 '채점됨' 그대로 → 횟수 차감 유지 (R4)
```

## 4. 상태 흐름 세 가지

### 4-1. 제출 상태 (`Submission.status`)

```
                 ┌─ 검사 통과 ─▶ 채점 대기 ─(worker)─┬─▶ 채점됨
 업로드 중 ──────┼─ 검사 실패 ─▶ 형식 오류           └─▶ 시스템 오류 (3회 실패)
 (시작 = 1회)    ├─ 10분 무수신 ▶ 만료
                 ├─ 참여자 취소 ▶ 취소
                 └─ (마감 후 시작) 검사 통과 ▶ 마감 후 접수
```

| 상태 | 횟수에 들어가나 | 이유 |
|---|---|---|
| 업로드 중, 채점 대기, 채점됨 | 들어감 | R6(동시 제출)을 막으려면 시작하는 순간 1회를 잡아 둬야 한다 |
| 형식 오류, 만료, 취소, 시스템 오류 | 빠짐 | R3·R4: 참여자 잘못이 아니거나 채점하지 않음 |
| 마감 후 접수 | 셈 대상 아님 | R2: 받기만 하고 채점하지 않음 |

횟수는 **칸에 저장하지 않고 매번 센다**(`count_used`). 엑셀의 COUNTIFS 수식과 같다.

### 4-2. 검토 상태 (`Submission.review_status`) — '채점됨'에만

```
 검증 대기 ─(관리자1 제안)─▶ 적합 제안 / 부적합 제안 ─(관리자2 결정)─▶ 적합(확정) / 부적합(확정)
     ▲   └──────────(관리자2 직접 결정)────────────────────────────▶        │
     └──── 반려(관리자2) / 재검토(관리자2, 사유 필수) ◀──────────────────────┘
```

- 바꾸는 길은 `review._change` 하나다. ① 제출 줄 행 잠금 → ② **화면을 연 뒤 다른 관리자가 바꿨으면 거부**(폼이 마지막 이력 번호를 숨겨 보냄) → ③ 상태·이력(`Review`)·감사 로그를 한 트랜잭션으로 저장한다.
- 참여자 화면에는 제안 두 가지를 모두 "검토 중"으로만 보여 준다. 확정 전의 의심을 다른 학생에게 알리지 않으려는 것이다(11/21 결정).
- **최종 성적 확정** [RFP 2·6쪽]: 리더보드의 대표 기록이 모두 '적합(확정)'이 되면 그 과제의 성적이 확정된 것이다. 관리자 '최종 성적' 화면이 확정 현황과 성적표 CSV를 주고, 참여자 리더보드에는 '최종 확정'이 표시된다. 재검토로 하나라도 풀리면 다시 '확정 아님'.

### 4-3. 작업 상태 (`Job.status`)

```
 대기 ─(claim)─▶ 실행 중 ─┬─ 성공 ─────────────▶ 완료 (채점이면 검증 Job 등록)
  ▲                      ├─ 실패, 시도 < 3 ──▶ 대기 (10초·20초 뒤)
  └── 15분 넘게 소식 없음 ┘└─ 실패, 시도 = 3 ──▶ 실패 (채점: 시스템 오류 / 검증: 리포트 '검증 실패')
      (worker가 죽은 것으로 보고 되돌림)
```

- 채점 Job이 검증 Job보다 먼저 실행된다(`PRIORITY`). 검증은 수십 초 걸리지만, 새 제출의 점수는 바로 나와야 하기 때문이다.

## 5. 앱별 설명과 읽을 파일

### accounts — 사용자

- `User`: 실명, 관리자2 여부. 대회별 역할은 여기가 아니라 `CompetitionMember`에 있다.
- 가입은 참여 코드가 필수다(R13). 관리자2는 서버 명령 `create_admin2`로만 만든다. 웹에서 스스로 관리자2가 될 길이 없다.
- 대입 공격 잠금(`throttle.py`): 아이디당 10분에 5회. 참여 코드는 IP당 20회로 둔다(강의실이 IP 하나를 공유하므로).
- 읽을 파일: `models.py` → `throttle.py` → `views.py`

### competitions — 대회·과제·권한

- `Competition`(참여 코드 8자리, 헷갈리는 글자 제외), `CompetitionMember`(역할·익명 별칭·활성), `Project`(지표·방향·컬럼), `ProjectFile`(학습·테스트 feature·정답), `Deadline`
- **권한 함수 3개(`permissions.py`)**: 남의 대회는 404로 존재를 숨기고, 소속인데 권한이 없으면 403이다. 모든 화면이 맨 앞에서 이 함수를 거친다.
- **저장소(`storage.py`)**: `private/`(정답), `shared/`(공개 파일), `submissions/`(제출). 어떤 URL에도 연결되지 않는다. 저장 이름은 UUID이고, 정규식으로 경로 조작을 막는다.
- `csvcheck.py`: 표준 `csv` 모듈로 내용을 검사한다(NUL 바이트, UTF-8, 칸 수, 중복 id, 허용 값).
- `load_demo` 명령: 예시 대회(손글씨 숫자, 계정 13개, 제출 11건)를 만든다. 여러 번 실행해도 된다.
- 읽을 파일: `permissions.py` → `storage.py` → `csvcheck.py` → `services.py`

### submissions — 제출·채점·리더보드·검토

| 파일 | 내용 |
|---|---|
| `services.py` | 제출 세 단계(시작·조각·완료)와 R1~R6. **규칙이 가장 많이 모인 파일** |
| `scoring.py` | 지표 4종(표준 라이브러리만), id로 맞춰 채점, 서버 오류 처리 |
| `leaderboard.py` | 대표 기록 고르기(`DISTINCT ON`), 공동 순위, 화면 4자리로 동점 비교 |
| `review.py` | 제안·결정·반려·재검토, 검토 목록(리더보드 함수 재사용), **일괄 확정**(대상은 리포트 단계가 아니라 '이유'로 고름: V3·V7은 참고·안내라 판정에 넣지 않음, V4 셸/실행 순서 '주의'는 가능, V1·V5 '주의'는 손수정 가능성이라 한 건씩. 건마다 `decide`를 그대로 써서 행 잠금·화면을 연 뒤 바뀜 거부·이력이 같다) |
| `results.py` | **최종 성적**: 대표 기록마다 확정/검토 중/미검토, 확정한 관리자·시각, 리더보드에 없는 참여자와 이유, 성적표 CSV(엑셀용 BOM, 수식 삽입 차단). 리더보드 함수 재사용 |
| `views.py` / `review_views.py` | 참여자 화면 / 관리자 화면 |

읽는 순서: `models.py` → `services.py` → `scoring.py` → `leaderboard.py` → `review.py` → `results.py`

### jobs — 작업 큐와 worker

- `Job` 테이블: 종류(채점·검증), 상태, 시도 횟수, 실행 예정 시각.
- `queue.claim`: `SELECT ... FOR UPDATE SKIP LOCKED`
  - `FOR UPDATE`: 고른 줄을 잠가 다른 worker가 같은 작업을 가져가지 못하게 한다.
  - `SKIP LOCKED`: 잠긴 줄은 기다리지 않고 건너뛴다 → worker를 늘려도 서로 막지 않는다.
  - 가져간 즉시 커밋한다 → 실행 중에 worker가 죽으면 '실행 중'이 남고, 15분 뒤 `recover_stale`이 되돌린다.
- `queue.run`: 결과 저장과 '완료' 표시를 한 트랜잭션으로 묶는다(둘 다 되거나 둘 다 안 됨).
- `housekeeping.py`(1분마다): 멈춘 작업 복구, 빠진 작업 등록, 방치된 업로드 만료, 하루 지난 로그인 실패 기록·버려진 제출 파일 삭제.
- 읽을 파일: `models.py` → `queue.py` → `management/commands/run_worker.py`

- **V7의 한계**: 출력 칸을 고친 것은 재실행 대조(⑥)로, 숫자를 직접 적은 것은 ⑦로 찾지만, 계산 결과를 일부러 바꿔 출력하는 코드(예: `scores.mean() + 0.1`)는 다시 실행해도 같은 값이 나와 못 잡는다. 샌드박스 쪽 출력 전달(`rerun_outputs.json`)은 샌드박스 이미지를 다시 빌드해야 생긴다. 코드를 읽기만 하므로 함수·변수로 감싼 처리는 놓치거나 '판정 불가'가 된다. 5% 기준은 와인 데모 정석 4개(차이율 −8.4% ~ +2.2%)로만 살펴본 임시 값이다.
- **시드 미고정 안내** (`checks.seed_hint`, 11/21): 정직한 노트북도 `random_state` 없이 학습하면 재실행 결과가 달라 V1이 '의심'이 될 수 있다(E2E에서 시드 없는 신경망: 재실행할 때마다 62.5%·23.1% 일치). V1이 주의·의심인데 V5(모델 예측)가 제출 CSV와 일치하면 V1에 "시드 미고정 가능성" 안내와 V4가 찾은 시드 없는 모델 이름을 붙인다. **판정은 낮추지 않는다** — 외운 답을 돌려주는 가짜 모델도 V5는 맞을 수 있기 때문이다. 사람이 노트북을 보고 판단한다.

**정답 파일은 샌드박스에 들어가지 않는다.** 넣는 것은 그 제출의 노트북·모델, 공개 `train.csv`, `test.csv`뿐이다. 테스트로 확인한다.

### 6-2. 결과 위조를 막는 방법

- 참여자 코드와 결과가 같은 공간에 있으면 노트북이 결과 파일을 고칠 수 있다. 그래서 다음처럼 만들었다.
  1. 실행기는 시작하자마자 표준 출력을 **자기만 아는 통로**(`os.dup`, 자식에게 상속되지 않음)로 빼 두고, fd 1·2는 `/dev/null`로 돌린다. 노트북과 그 자식 프로세스가 무엇을 출력해도 결과 통로에는 닿지 않는다.
  2. 결과는 파일이 아니라 그 통로로 한 번에 내보내고, worker는 컨테이너 로그(표준 출력)에서 읽는다.
  3. V5(모델)와 V1(노트북)을 **다른 컨테이너**에서 돌린다. 노트북이 남긴 프로세스가 모델 검사 결과에 손댈 수 없다.
  4. **1만으로는 부족했다(2026-11-21 E2E 시험에서 실제 재현).** 노트북 커널도 실행기와 같은 uid(1000)라서 `/proc/1/fd/<번호>`를 열면 1의 통로에 직접 쓸 수 있었다. 가짜 "ok" 블록을 계속 쓰는 프로세스를 남기자 worker가 3번 모두 가짜 결과를 받았다. 그래서 두 겹을 더했다.
     - 실행기가 노트북을 돌리기 전에 자기 자신을 **dump 불가**(`prctl(PR_SET_DUMPABLE, 0)`)로 만든다 → 같은 uid라도 `/proc/1/fd`·`/proc/1/environ`을 열 수 없다(실패하면 노트북을 실행하지 않는다).
     - worker가 컨테이너마다 **무작위 키**를 만들어 환경변수로 넘기고, 실행기는 읽자마자 환경에서 지운 뒤 결과에 **HMAC 서명**을 붙인다. worker는 서명이 맞는 블록만 받는다(`verification/sandbox.py parse_output`). 가짜 블록만 있으면 "판정 불가"가 된다.
     - 실제 샌드박스 테스트가 `/proc/1/fd` 쓰기·`/proc/1/environ` 읽기 차단과 키 미상속을 확인한다.
- 노트북이 "스스로 만든 CSV"는 노트북 마음대로다. 이것은 위조가 아니라 V1이 원래 재는 대상이다("이 노트북을 실행하면 이 CSV가 나온다"). 정답을 코드에 적어 둔 경우는 V4가 잡는다.

### 6-3. Docker 소켓 위험

- Docker 소켓에 접근하면 호스트 root 권한과 사실상 같다. 그래서 다음 세 가지를 했다.
  1. web에는 소켓도 프록시 주소도 없다. web은 프록시가 있는 내부망에 아예 없다(이름 조회조차 실패하는 것을 확인했다).
  2. worker는 프록시를 거친다. 프록시는 `/containers` API와 POST만 허용하고, 이미지·볼륨·네트워크·exec 실행·빌드·시스템 정보는 403이다(확인했다).
  3. worker는 외부 요청을 받지 않고, 컨테이너 옵션은 코드에 고정되어 있다.
- **한계**: 프록시는 API 종류만 보고, 컨테이너 생성 옵션(예: 특권 모드)은 검사하지 않는다. worker 코드가 탈취되면 위험하다. 운영 권장 사항은 gVisor(`runsc`) 런타임이다.

## 8. 주요 설계 결정과 버린 대안

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| Django + 템플릿 (D1) | 인증·CSRF·세션·ORM·자동 이스케이프가 내장되어 직접 쓰고 설명할 코드가 적다 | FastAPI + React: 코드베이스 2개, 인증·CSRF 직접 구현 |
| DB 테이블 큐 (D2) | 구성 요소가 하나 적고, worker가 죽어도 작업이 남는다 | Celery + Redis |
| 업로드 세션 = 제출 한 줄 | 횟수 세기가 쿼리 하나. "업로드 중" 상태가 세션 역할 | 세션 테이블 별도 |
| 1MB 조각 업로드 | "10분 무수신 만료"를 글자 그대로 구현, 진행률 표시 | 한 번에 전송 |
| 순위·횟수 저장 안 함 | 매번 계산하면 실제와 어긋날 수 없다. 참여자 수십 명이라 빠르다 | 캐시 칸 |
| 동점 = 화면 4자리, 사사오입 함수 하나 | 보이는 숫자가 같으면 순위도 같다. Python `round(0.90025, 4)` = 0.9002 문제 | 6자리 비교 |
| 검토 상태 칸 + 이력 테이블 | 쿼리는 칸 하나로, "누가 왜"는 이력으로 | 이력만 두고 매번 계산 |
| V1을 핵심으로 | RFP 8쪽이 노트북 실행 검증을 직접 언급. 손으로 만든 CSV를 잡는 유일한 방법 | 해시·정적 검사만 |
| V1·V5를 다른 컨테이너로 | 노트북이 모델 검사 결과에 손대지 못하게 | 한 컨테이너 |
| 노트북 HTML은 그리지 않음 | 걸러내기(sanitize)는 빠뜨릴 수 있다. 처음부터 안 그리면 실수할 곳이 없다 | nh3로 걸러서 표시 |

### 11-4. 잡을 수 있는 부정과 없는 부정

시스템은 **판정하지 않고 근거를 만든다.** 판정은 관리자1 제안 → 관리자2 결정(R10~R12).

| 구분 | 부정 방법 | 대응 |
|---|---|---|
| 구조로 막음 | 점수 직접 조작 | 점수는 worker가 서버에서 계산. 브라우저는 점수를 보내지 않음 |

**정답을 직접 적은 노트북은 V1을 통과한다**(다시 실행해도 같은 CSV). 그래서 V4가 필요하다.

### 11-5. 예시 대회 데이터

| 과제 | 원본 | 지표 | 행(학습/테스트) |
|---|---|---|---|
| 손글씨 숫자 (`demo/data/digits`) | sklearn `load_digits`(8×8 픽셀, 값 0~16 그대로, 행 섞고 새 id) | Accuracy (10종 분류) | 1437 / 360 |

**문제**: 정답이 sklearn 패키지 안에 들어 있다. 샌드박스 네트워크를 끊어도 `load_digits()`는 동작한다. test feature 행을 원본에서 찾으면 만점이고, V1 재실행도 통과한다(예시 demo_stu08).

**대책**
1. V4가 `sklearn.datasets`의 `load_*`·`fetch_*` 호출을 "공개 정답 데이터 사용 의심"으로 표시한다
2. test는 100행 이상 → 리더보드 점수 변화로 한 줄의 정답을 추정하기 어렵게
3. 실제 대회에서는 공개되지 않은 데이터(또는 공개 학습셋 일부를 떼어 낸 것)를 정답으로 쓰도록 안내한다

**확인한 사실 (2026-11-21)**: feature에 표준편차 1% 잡음을 넣어도 **최근접 이웃 조회를 막지 못했다**(개발 중 유방암 데모 1.0000). 그래서 잡음은 넣지 않고 V4로 잡는다. 만드는 법: [demo/README.md](../demo/README.md)
