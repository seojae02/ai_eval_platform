# AI 모델 성능평가 자동화 플랫폼

## 예시 계정 (로컬 시연용)

`./dev.sh start` → `./dev.sh demo` 후 <http://127.0.0.1:8000> 에서 로그인합니다. **비밀번호는 아이디와 같습니다.**

| 아이디 | 비밀번호 | 역할 | 해 볼 것 |
|---|---|---|---|
| `demo_prof` | `demo_prof` | 관리자2 (교수) | 승인 대기 → 최종 결정, 최종 성적(성적표 CSV), 대회 개설·정답 등록 |
| `demo_ta` | `demo_ta` | 관리자1 (조교) | 과제 → **검토** → 검증 리포트·노트북 보기 → 적합/부적합 제안 |
| `demo_stu01` ~ `demo_stu11` | 아이디와 같음 (예: `demo_stu01`) | 참여자 (학생) | 과제 화면에서 제출, 내 점수·남은 횟수, 익명 리더보드 |

> 이 계정은 `load_demo`가 로컬 DB에 만드는 가상 계정입니다. 서버에 올린 곳에서는 `load_demo`를 실행하지 마세요.

## 무엇을 하는 서비스인가

참여자가 낸 **예측 CSV를 자동 채점**하고, 그 CSV가 **정말 모델의 추론 결과인지 근거를 모아** 관리자가 검토·승인하게 돕는 웹 서비스입니다. (순천향대 사물인터넷학과 AI모델 성능평가 자동화 경진대회 출품작)

```
참여자: CSV·노트북·모델 제출 ─▶ 형식 검사 ─▶ 자동 채점 ─▶ 리더보드(익명, 미검증 표시)
                                              │
                                              ▼
                     검증 리포트 V1~V7 (노트북 다시 실행, 모델 다시 예측, 복사·수정 흔적)
                                              │
                         관리자1 제안 ─▶ 관리자2 결정 ─▶ 최종 성적 확정
```

- 시스템은 **판정하지 않고 근거를 보여 줍니다.** 애매한 신호는 '참고'로만 표시하고, 최종 판단은 사람이 합니다(RFP 6쪽: 관리자1 제안 → 관리자2 승인).
- 공식 점수는 CSV 기준입니다(RFP 5쪽). 검증은 점수·순위를 바꾸지 않습니다.

더 자세한 문서: 역할별 사용법 [docs/SCENARIOS.md](docs/SCENARIOS.md), 구조·설계 이유·규칙 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), 예시 자료 [demo/README.md](demo/README.md)

## 실행

필요한 것: Docker + Docker Compose, git, bash (호스트에 Python 불필요)

```bash
git clone <저장소 주소> ai-eval-platform && cd ai-eval-platform
./dev.sh start     # .env 자동 생성(무작위 비밀값) → 빌드 → 실행 → 접속 확인. 처음에는 몇 분
./dev.sh demo      # 예시 대회 불러오기(계정 13개, 제출 11건). 여러 번 실행해도 됨
```

- "→ http://127.0.0.1:8000 열림"이 나오면 브라우저로 엽니다.
- 예시 제출 11건은 몇 초 안에 채점되고, 노트북 재실행 등 검증까지 약 2분 걸립니다(2026-11-25, 새 폴더에서 처음부터 실행해 1분 40초). 그동안 화면에 진행 단계가 보입니다.

| 명령 | 하는 일 |
|---|---|
| `./dev.sh start` / `stop` / `status` | 실행 / 멈춤(데이터 유지) / 상태 |
| `./dev.sh demo` | 예시 대회 불러오기 |
| `./dev.sh logs web` | 로그 보기(`worker`, `db`도 가능) |
| `./dev.sh restart` | web·worker 다시 시작(worker 코드를 고친 뒤) |
| `./dev.sh test` | 자동 테스트 (2026-11-25: 698 passed) |
| `./dev.sh test-sandbox` | 실제 샌드박스 컨테이너로 격리 확인 테스트 |
| `./dev.sh admin2` | 실제 대회용 관리자2 계정 만들기(웹에서는 만들 수 없음) |
| `./dev.sh reset` | **DB를 지우고** 처음부터(묻고 진행) |
| `./dev.sh prod` | 운영 모드(gunicorn, `DEBUG=False`). HTTPS는 앞단 프록시 + `.env`의 `DJANGO_HTTPS=True` |

**안 될 때**: web이 안 뜨면 `./dev.sh logs web`. 로그에 `password authentication failed`가 있으면 `.env`와 DB 비밀번호가 다른 것이므로 `./dev.sh reset` 후 `./dev.sh demo`. 8000번 포트가 이미 쓰이면 그 프로그램을 멈추세요.

과제: 손글씨 숫자 10종 분류(정확도, test 360행). 정상 3명, 부정 7명, 방법 실수 1명. `demo_ta`로 로그인해 **검토** 화면을 열면 다음처럼 나옵니다(2026-11-25 실제 실행 결과).

| 계정 | 한 일 | 점수 | 전체 판정 | 근거 |
|---|---|---|---|---|
| demo_stu01 | 정상: 과제 PDF 코드 그대로(SGD) | 0.9389 | 문제 없음 | - |
| demo_stu02 | 정상: 특성 추가 + 랜덤 포레스트 | 0.9917 | 의심 | V2: demo_stu04와 CSV가 똑같음. **"이 제출이 먼저"**가 함께 표시됨 → 복사당한 원본(누가 원본인지는 관리자가 판단) |
| demo_stu03 | 정상: 스케일러+SVC 파이프라인 | 0.9861 | 문제 없음 | - |
| demo_stu04 | 부정: 친구(02) CSV를 받아 제출 | 0.9917 | **의심** | V1 86.1% 불일치, V2 같은 CSV(상대가 먼저), V5 86.1%, V6 다른 50행이 정답 쪽 |
| demo_stu05 | 부정: 저장된 CSV를 엑셀에서 4행 고침 | 0.9889 | **주의** | V1·V5 98.9%, V6 다른 4행 모두 정답 쪽 |
| demo_stu06 | 부정: 노트북 안에서 라벨 20개를 직접 적어 덮어씀 | 0.9972 | **주의** | V1은 통과(재실행해도 같음) → V6: 모델 예측과 다른 2행이 모두 정답 쪽 |
| demo_stu07 | 부정: 다른 곳에서 만든 예측 열을 붙여 넣음 | 0.9944 | **의심** | V4 값 직접 입력(숫자 문자열), V5 92.8% |

| demo_stu09 | 부정: 노트북 CV 출력 칸을 3%p 높게 고침 | 0.9778 | 문제 없음 | V7 주의: 노트북 CV 0.9925 ↔ 다시 실행 0.9645 |
| demo_stu10 | 부정: `print('Mean: 0.9900')`처럼 숫자로 적음 | 0.8917 | 문제 없음 | V7 주의: CV 값 직접 입력 |
| demo_stu11 | 방법 실수: CV 전에 PCA를 전체 데이터에 fit | 0.9972 | 문제 없음 | V7 주의: 전처리 순서 |

- demo_stu09·10(노트북 CV 위조)은 공식 점수(CSV)와 무관해 전체 판정은 '문제 없음'이지만, 관리자 화면의 **방법 점검** 칸과 학생 화면에 '확인 필요'로 보입니다.

## 검증 리포트 V1~V7

| 검사 | 보는 것 | 잡는 것 (RFP 8쪽 "모델 추론 결과인가, 우회적 수행인가") | 판정 |
|---|---|---|---|
| V1 노트북 재실행 | 격리 컨테이너에서 노트북을 처음부터 실행 → 나온 CSV와 제출 CSV 비교 | CSV 손수정, 노트북과 다른 CSV | 99%↑ 일치 / 90~99% 주의 / 미만 의심 |
| V2 같은 파일 | 다른 참여자와 CSV·노트북 SHA-256이 같은지 | 남의 CSV를 그대로 제출 | 의심 (양쪽 모두, "누가 먼저" 함께 표시) |
| V3 오답 일치율 | 다른 참여자와 같은 행에서 같은 오답(회귀: 같은 값)의 비율 | 남의 CSV를 조금 고쳐 제출 | **참고만** (70%↑이면 비교 대상 표시) |
| V4 노트북 정적 검사 | 실행하지 않고 코드 분석: 실행 순서, 학습·예측·저장 유무, 값 50개↑ 직접 입력, 공개 원본(`sklearn.datasets`)·제공하지 않은 파일 읽기 | 정답·예측 직접 입력, 원본에서 정답 조회 | 주의·의심 |
| V5 모델 재예측 | 제출한 모델 파일로 test를 다시 예측 → 제출 CSV와 비교 | 모델 없이 만든 CSV, 겉치레 모델 | V1과 같은 기준 |
| V6 수정 흔적 | 재실행·모델 예측·제출 CSV를 서로 비교, 다른 행이 정답 쪽으로 쏠렸는지 | 몇 줄만 고친 CSV(V1이 '주의'에 그치는 경우), 노트북 안에서 라벨 덮어쓰기 | 5행↑·90%↑ 정답 쪽이면 의심 |
| V7 학습·평가 방법 | CV 전 전처리, 중복 행, 평가 지표, 노트북 CV ↔ 서버 점수·다시 실행한 CV, CV 값 직접 입력 | AI가 만든 잘못된 검증 코드, 노트북 CV 위조 | **안내만** (전체 판정 제외) |

## 보안 요약

- **Django 기본**: CSRF, 템플릿 자동 이스케이프, ORM(SQL 삽입 방지), 클릭재킹 헤더
- **설정**: argon2 해시, 비밀번호 규칙, 세션 8시간, HttpOnly·SameSite 쿠키, 엄격한 CSP(인라인 스크립트·외부 CDN 금지), HTTPS 운영 설정
- **직접 구현**: 로그인·참여 코드 대입 잠금, 남의 대회는 404로 숨김, 정답 비공개 저장소(URL 없음), UUID 저장 이름, 업로드 내용 검사, 추가 전용 감사 로그, 임시 비밀번호 1회 표시 + 강제 변경
- **샌드박스**: 제출마다 새 컨테이너. 네트워크 없음, 읽기 전용, 메모리 2GB, CPU 1개, 권한 제거, root 아님, 시간 제한. 정답·비밀값·DB 주소 없음. worker는 Docker 소켓 대신 API를 제한한 프록시를 거치고, web·worker는 pickle 모델을 열지 않음

## 서비스 장애 시 대책 [RFP 8쪽]

| 상황 | 대책 | 위치 |
|---|---|---|
| web·worker·프록시 컨테이너가 죽음 | 자동으로 다시 뜸(`restart: unless-stopped`) | `docker-compose.yml` |
| 채점·검증 작업이 일시적 오류로 실패 | 10초·20초 뒤 재시도, 3번째 실패면 '시스템 오류'로 끝내고 **제출 횟수는 차감하지 않음**(RFP 5쪽) | `jobs/queue.py` |
| worker가 작업 도중 멈춤 | 1분마다 멈춘 작업을 찾아 되돌리고, 빠진 작업을 다시 등록 | `jobs/housekeeping.py` |
| 업로드가 중간에 끊김 | 10분 동안 조각이 안 오면 만료, 횟수 미차감. 마감 전에 **시작**한 업로드는 그 마감으로 인정 | `submissions/services.py` |
| 검증(샌드박스)이 실패·시간 초과 | 리포트에 '판정 불가'로 남고 사람이 확인. **점수·순위는 영향 없음**(채점은 검증과 따로, 항상 먼저 처리) | `verification/services.py` |
| DB·파일 손실 | 아래 명령으로 백업·복구(2026-11-25 임시 DB에 복구해 제출 수 일치 확인) | - |

```bash
# 백업: DB와 업로드 파일(storage/)
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backup.sql
tar czf storage-backup.tgz storage/
# 복구: 빈 DB에 되돌리기(./dev.sh reset 직후 등)
docker compose exec -T db sh -c 'psql -q -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < backup.sql
tar xzf storage-backup.tgz
```

백업 파일에는 계정의 비밀번호 해시와 제출 기록이 들어 있으므로 저장소에 올리지 말고 안전한 곳에 둡니다.

## 검증 시간 단축 [RFP 8쪽]

- **노트북·가중치 파일로 자동 검증**: 사람이 노트북을 돌려 보지 않아도 격리 컨테이너가 노트북을 다시 실행(V1)하고 모델 파일로 다시 예측(V5)해 일치율을 보여 줍니다.
- **빠른 근거 먼저**: 파일 비교·코드 분석(V2·V3·V4, 몇 초) → 모델 재예측(V5) → 노트북 재실행(V1, 가장 오래 걸림) 순서로 진행하고, 단계와 대기열 위치를 화면에 보여 줍니다.
- **채점이 항상 먼저**: 채점 작업은 검증보다 우선 처리되어, 검증이 밀려도 점수·리더보드는 바로 나옵니다.
- **사람이 볼 것만 골라 줌**: 검토 목록은 점수 높은 기록부터, 근거가 약한 '주의'만 있는 제출은 관리자2가 **일괄 확정**할 수 있습니다.
- **확장 방안(미구현)**: 학습 셀을 건너뛰고 제출한 모델로 추론만 다시 실행, worker 수 늘리기, 참여자별 대표 기록만 노트북 재실행.

## 가정과 한계

**RFP에 없어 정한 것**: 제출 횟수는 마감 구간별로 셈 · 리더보드는 과제당 하나(모든 구간의 최고점) · 관리자1은 관리자2가 대회별 지정 · 동점은 소수 4자리로 비교 · 참여자 화면에는 확정 전 제안을 "검토 중"으로만 표시

**한계**
- 대리 작성·다중 계정은 기술로 막을 수 없습니다.
- 정답을 코드에 적은 노트북은 재실행(V1)을 통과합니다 → V4(값 50개↑)·V6(몇 줄)이 표시하고 사람이 확인합니다.
- 무작위 시드를 고정하지 않은 정직한 노트북은 V1이 어긋날 수 있습니다. 모델 예측(V5)이 맞으면 리포트에 시드 안내가 붙습니다. 참여자 안내: `random_state` 고정.
- 노트북 **밖에서** 만든 특성으로 학습한 모델은 test.csv만으로 예측할 수 없어 V5가 '주의'입니다. 참여자 안내: 전처리를 `Pipeline` 안에 넣어 저장.
- 계산 결과를 일부러 바꿔 출력하는 코드(`scores.mean() + 0.1`)는 재실행해도 같은 값이라 V7이 못 잡습니다.
- 검증은 scikit-learn 계열만 완전히 지원합니다(PyTorch·TensorFlow 모델은 V5 '판정 불가'). 노트북 재실행은 CPU 1개·셀 2분·전체 4분 제한이며, 넘으면 '판정 불가'로 사람이 확인합니다(점수·순위에는 영향 없음).
- worker 1개가 검증을 한 건씩 처리합니다. 제출이 몰리면 리포트가 늦게 나옵니다(대기열 위치를 화면에 표시).
- 감사 로그는 앱에서 수정·삭제가 막혀 있지만 DB에 직접 SQL을 쓰면 우회할 수 있습니다.
